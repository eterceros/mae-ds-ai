# Antes y después: qué cambia y cuánto

Cada fila es un problema de la carpeta [`antes/`](antes/), el cambio que lo corrige en [`despues/`](despues/) (marcado en el archivo con un comentario `# CORRECCIÓN:`) y la cifra que se midió en la demo. Las cifras salen de [`results/`](results/) (24 oct 2026, un portátil con Windows 11 y Docker Desktop 29.9.2; detalle de la máquina en cada archivo). Los tiempos son la mediana de 3 corridas; los arranques de K5, 5 corridas por caso.

| Problema | Dónde en `antes/` | Cambio en `despues/` | Cifra medida |
|---|---|---|---|
| Imagen base completa con todo lo que se usó para compilar (TypeScript, @nestjs/cli, `src/`, caché de npm) | [`Dockerfile`](antes/Dockerfile): `FROM node:24`, una sola etapa | [`Dockerfile`](despues/Dockerfile): multi-stage; la etapa final solo copia `dist/` y las dependencias de producción, sobre `node:24-slim` | **K1:** 1,74 GB → 357 MB en disco; 429 MB → 83,4 MB comprimida; 166 → 102 paquetes en `node_modules` (65 → 24 MB) |
| `COPY . .` antes de instalar: tocar una línea de código reinstala todas las dependencias | [`Dockerfile`](antes/Dockerfile): `COPY . .` y luego `RUN npm install` | [`Dockerfile`](despues/Dockerfile): primero `package*.json` y `npm ci`, después `src/` | **K1:** rebuild tras cambiar `src/main.ts`: 9,4 s → 2,4 s; reinstaló dependencias en 3 de 3 → 0 de 3 |
| Sin `.dockerignore`: todo el contexto entra a la imagen | [`Dockerfile.dockerignore`](antes/Dockerfile.dockerignore) vacío | [`api/.dockerignore`](api/.dockerignore) excluye `node_modules`, `dist`, `.env`, `.git` | Sin cifra propia (el contexto de la demo no tiene `node_modules` local); el efecto sobre secretos se ve en K4 |
| Etiqueta flotante y sin digest: el mismo Dockerfile puede dar otra imagen mañana | [`Dockerfile`](antes/Dockerfile): `node:24` | [`Dockerfile`](despues/Dockerfile): `node:24.22.1-bookworm-slim@sha256:55fb…` | Sin cifra (es reproducibilidad). **K7:** hadolint no lo marca |
| Base con cientos de paquetes que la API no usa | [`Dockerfile`](antes/Dockerfile): `node:24` (Debian completo) | [`Dockerfile`](despues/Dockerfile): `node:24-slim`; otras opciones en [`bases/Dockerfile`](bases/Dockerfile) | **K2 (Trivy):** 4641 CVE (21 críticas, 618 altas) → 245 (1 crítica, 62 altas) con slim; 16 con Alpine; 32 con distroless o Docker Hardened Image |
| Corre como root: si alguien toma el proceso, puede reescribir el código y el sistema del contenedor | [`Dockerfile`](antes/Dockerfile): sin `USER` | [`Dockerfile`](despues/Dockerfile): `USER node`, archivos de root copiados sin `--chown` | **K3:** uid 0 → 1000; 14 → 0 capacidades efectivas; 3 de 3 escrituras peligrosas posibles → 0 de 3 |
| `npm` como PID 1 (señales y apagado, S02) | [`Dockerfile`](antes/Dockerfile): `CMD ["npm", "run", "start"]` | [`Dockerfile`](despues/Dockerfile): `CMD ["node", "dist/main.js"]` | **K3:** 3 procesos (`npm` → `sh` → `node`) → 1 (`node` es el PID 1) |
| Token de build en `ARG`: queda en el historial de la imagen | [`Dockerfile.secreto`](antes/Dockerfile.secreto): `ARG NPM_TOKEN` + `--build-arg` | [`Dockerfile.secreto`](despues/Dockerfile.secreto): `RUN --mount=type=secret,id=npm_token,env=NPM_TOKEN` | **K4:** token visible en `docker history --no-trunc`: sí → no; BuildKit avisa `SecretsUsedInArgOrEnv` en la versión de antes |
| `COPY .env` y luego `RUN rm .env`: el archivo sigue en una capa | [`Dockerfile.secreto`](antes/Dockerfile.secreto) y su `.dockerignore` vacío | [`Dockerfile.secreto`](despues/Dockerfile.secreto): sin `COPY .env`; [`.dockerignore`](despues/Dockerfile.secreto.dockerignore) excluye `.env` | **K4:** hallazgos al recorrer `docker save`: 3 (el `.env` completo en una capa, su marca de borrado y el token en los metadatos) → 0 |
| `depends_on` sin condición: la API arranca antes de que Postgres acepte conexiones y muere | [`compose.yaml`](antes/compose.yaml): `depends_on: [postgres]`, sin healthcheck | [`compose.yaml`](despues/compose.yaml): healthcheck `pg_isready -h 127.0.0.1` + `condition: service_healthy` | **K5:** con volumen vacío, la API arrancó bien en 0 de 5 → 5 de 5 (con volumen ya inicializado, 5 de 5 en los dos: la carrera se ganó en esta máquina) |
| Healthcheck que pregunta por el socket Unix (el servidor temporal de inicialización responde por ahí) | [`compose.healthcheck-socket.yaml`](antes/compose.healthcheck-socket.yaml): `pg_isready` sin `-h` | [`compose.yaml`](despues/compose.yaml): `pg_isready -h 127.0.0.1` (TCP, el camino de la API) | **K5:** no se reprodujo (5 de 5 bien en los dos); es una carrera de fracciones de segundo. Costo del chequeo por TCP: la API arranca ~0,7 s más tarde |
| Sin paso de migraciones: o se migra a mano, o cada réplica de la API migra al arrancar | [`compose.yaml`](antes/compose.yaml): no hay | [`compose.yaml`](despues/compose.yaml): servicio `migrate` que corre una vez; la API espera `service_completed_successfully` | **K6:** orden garantizado en 3 de 3 (Postgres sano 1,25 s → `migrate` 1,75–1,95 s → API 2,45 s); con una migración rota, `up --wait` sale con código 1 y la API **no arranca**; la segunda vez aplica 0 migraciones |
| Dockerfile generado por IA usado sin revisar | [`Dockerfile.ia-gordon`](antes/Dockerfile.ia-gordon) y [`Dockerfile.ia-smollm2`](antes/Dockerfile.ia-smollm2) | [`Dockerfile.ia-gordon-revisado`](despues/Dockerfile.ia-gordon-revisado): digest, sin `--chown` en el código, dependencias de producción en su propia etapa | **K7:** el de smollm2 no construye (base inexistente); el de Gordon construye, pero el proceso **puede reescribir su propio código** → revisado: no. hadolint dio 1 aviso menor en ambos y ninguno sobre esto |
| Docker → Podman: stack que solo corre bien en Docker (nombres cortos de imagen, `HEALTHCHECK` en el Dockerfile, que el formato OCI de Podman no guarda) | [`Dockerfile`](antes/Dockerfile): `FROM node:24` (nombre corto) | [`Dockerfile`](despues/Dockerfile) y [`compose.yaml`](despues/compose.yaml): registro completo (`docker.io/library/...`), healthchecks en el compose, solo puertos altos (rootless no publica < 1024), sin *bind mounts* en el stack base | **K8:** con Podman 5.8.3 rootless corrió **sin tocar ningún archivo**: misma imagen (249,2 MB sin comprimir, mismas capas de la base), build en frío 18,7 s (11,7 s con `--jobs 3`) frente a 7,0 s; `/salud` a los 4,0 s con el proveedor docker-compose y 9,6 s con podman-compose (Docker: 3,4 s); API uid 1000 dentro y uid 525287 sin privilegios en la VM. **Con podman-compose 1.6.0 la migración rota no frena la API** (`service_completed_successfully` solo espera que `migrate` termine) y `migrate` corre dos veces |

## Lo que no está en esta tabla

- **K2** compara cinco bases y no es un antes/después: elegir la base es una decisión con costos (sin shell no hay `docker exec ... sh`; Alpine usa musl). Ver [`results/K2_BASES.md`](results/K2_BASES.md).
- La única CVE alta de las dependencias de la propia API (`multer 2.4.0`, que trae `@nestjs/platform-express`) está en **todas** las variantes: cambiar la base no la arregla; hay que actualizar la dependencia (K2).
- **K8** compara motores, no versiones del stack: lo que cambió entre Docker y Podman no fue ningún archivo, sino el programa que interpreta el compose. Ver [`results/K8_PODMAN.md`](results/K8_PODMAN.md).
- El [`Dockerfile` de Spring Boot](despues/spring/Dockerfile) es una plantilla **no medida**.
